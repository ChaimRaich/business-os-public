# Business OS — Inventory

קליטת סחורה וסנכרון מלאי לעסקים קטנים ובינוניים. האפיון המלא ב-[SPEC.md](SPEC.md).

## Stack

- Next.js 16 (App Router, Cache Components), React 19, Tailwind 4, עברית RTL
- Supabase: Postgres, Auth, Row Level Security, מיגרציות SQL ב-`supabase/migrations`

## הרצה מקומית

דרוש Docker פועל (למשל `colima start`).

```bash
npm install
npx supabase start          # מסד, Auth ו-Studio מקומיים; מריץ את המיגרציות
cp .env.example .env.local  # ולהדביק את ה-Publishable key מתוך `npx supabase status`
npm run dev                 # http://localhost:3000
```

Studio: http://127.0.0.1:54323 · אימיילים מקומיים (Mailpit): http://127.0.0.1:54324

## קטלוג

- **מוצר** הוא דגם; כל פריט שנמכר הוא **וריאציה** שלו (מידה, צבע). למוצר תמיד יש לפחות וריאציה אחת.
- לכל וריאציה כמה **קודים** שרוצים: ברקוד, מק״ט ספק, מק״ט קופה, מזהה באתר. הקוד נשמר כטקסט בדיוק כפי שהודפס (אפסים מובילים נשמרים); ההתאמה והחיפוש מתעלמים מאותיות גדולות/קטנות.
- ברקוד, מק״ט קופה ומזהה באתר ייחודיים בעסק. מק״ט ספק הוא קוד דגם ויכול לחזור בכמה וריאציות.
- חיפוש (`search_products`) לפי שם מוצר, שם ספק, שם וריאציה או חלק מכל קוד.
- לכל עסק נוצר מחסן ברירת מחדל; מחסנים נוספים מנוהלים בהגדרות.

## קליטת סחורה

- מעלים צילום או PDF של תעודת משלוח / חשבונית (עד 10 קבצים למסמך). הקבצים נשמרים באחסון פרטי תחת `<business_id>/<document_id>/`.
- Claude קורא את המסמך ומחזיר שורות מובנות: מק״ט ספק, ברקוד, תיאור, וריאציה, כמות, עלות לפני מע״מ ומחיר צרכן. ערך שלא מודפס נשאר ריק; ערך שלא נקרא בוודאות מסומן לבדיקה.
- במסך האימות עורכים את השורות מול המסמך המקורי. המערכת מתריעה על אי-התאמה בין השורות לסכומים המודפסים ועל מסמך שכבר הועלה.
- כל שורה מותאמת לקטלוג לפי ברקוד, ואם אין, לפי מק״ט ספק כשהוא מצביע על וריאציה אחת בלבד.
- שורה שלא נמצאה: **יצירת מוצר חדש** מפרטי השורה (או וריאציה חדשה של מוצר עם אותו מק״ט ספק), או **שיוך למוצר קיים** בחיפוש. שיוך ידני נשמר גם אחרי שמירה והתאמה מחדש.
- התאמה לפי מק״ט ספק לא נעשית כשהווריאציה סותרת את השורה (ברקוד אחר או שם וריאציה אחר).
- **המלאי מתעדכן רק באישור הקליטה.**

## מלאי

- כל שינוי הוא **תנועה** (`stock_movements`): קליטה או התאמה. היתרה לכל פריט ומחסן (`stock_balances`) מתעדכנת בטריגר, באותה טרנזקציה. למשתמשים אין הרשאת כתיבה ישירה לאף אחת מהן.
- אישור (`approve_document`) דורש ספק, ולכל שורה מוצר וכמות. הוא קורה פעם אחת: נעילת שורה, ואינדקס ייחודי על (מסמך, פריט). אותו פריט בכמה שורות נקלט כסכום.
- מסמך מאושר נעול במסד, כולל השורות והקבצים. החריג היחיד: השלמת עלות שהייתה ריקה, כל עוד לא נוצר קובץ.
- תיקון נעשה ב**התאמת מלאי** (בעלים ומנהל): תנועה עם סיבה. שליחה כפולה של הטופס נרשמת פעם אחת, ואי אפשר לרדת מתחת לאפס.

## תמחור, ברקוד וקובץ לקופה

- מחיר לשדה ריק: מה שהוקלד, אחרת המחיר של המוצר, אחרת כלל הספק (ברירת מחדל: מועדון = עלות × 2.9, מכירה = מועדון + 10%, מעוגלים לשקל). מוצר קיים **שומר על המחיר שלו** גם כשהעלות השתנתה.
- סוג המוצר מוצע מתוך תיאור הספק; חומר לא מנוחש.
- ברקוד פנימי: `N` + קוד הספק בקופה + 6 ספרות רצות, נשמר כמק״ט קופה. מק״ט קופה שכבר קיים לא מוחלף.
- מחלקות לפי סוג מוצר מוגדרות בהגדרות.
- קובץ `.xls` עם 12 העמודות שב-`SPEC.md` סעיף 6, שורה לכל פריט (כמויות מסוכמות, עלות בממוצע משוקלל). לא נוצר עד שכל הפרטים מלאים. נשמר פעם אחת, והורדה חוזרת מחזירה את אותם בתים.
- סטטוס בקופה נשאר **ממתין** עד סימון ידני.

### הנחות שעדיין לא אושרו

נבנו לפי קובץ הדוגמה; לפני העלאה לקופה אמיתית צריך לאשר:

1. תמיד ברקוד פנימי, גם כשלספק יש ברקוד.
2. כלל התמחור חל על כל הספקים (ניתן לשינוי בכרטיס הספק). מחיר צרכן מודפס מוצג בלבד.
3. קודי ספק ומחלקה שאינם בקובץ הדוגמה (למשל לצמידים) צריך להזין ידנית.
4. לא ידוע אם העלאת ברקוד קיים מוסיפה כמות בקופה או מחליפה אותה. כשיש פריט כזה נדרש אישור מפורש לפני יצירת הקובץ.

### חיבור למודל

מגדירים ב-`.env.local` אחת משתי האפשרויות (פירוט ב-`.env.example`):

- **Azure (Microsoft Foundry):** `ANTHROPIC_FOUNDRY_API_KEY`, `ANTHROPIC_FOUNDRY_RESOURCE`, ו-`EXTRACTION_MODEL` = שם ה-deployment.
- **Anthropic API:** `ANTHROPIC_API_KEY`.

בלי מפתח, מסמך שמועלה מסומן "הקריאה נכשלה" עם הסבר, ואפשר להזין את השורות ידנית.

### בדיקת איכות החילוץ

```bash
npm run eval:extraction -- path/to/invoice.pdf
```

מריץ חילוץ אמיתי ומשווה שורה-שורה לתוצאה הצפויה שב-`SPEC.md` (סעיפים 13.1, 13.2). כל הרצה צורכת קרדיט.

## הפרדת נתונים והרשאות

- כל טבלה עסקית נושאת `business_id`; מדיניות RLS מתירה גישה רק לחברי העסק דרך `private.is_member` / `private.role_in`.
- תפקידים: `owner` (בעלים), `manager` (מנהל), `staff` (עובד). רק בעלים משנה שם עסק ומנהל משתמשים; בעלים ומנהל מוחקים מוצרים ומנהלים מחסנים; כל חבר בעסק מוסיף ועורך מוצרים וספקים.
- שורות בנות (וריאציות, קודים) מצביעות על האב דרך `(id, business_id)`, כך ששורה לא יכולה להתחבר לנתונים של עסק אחר.
- עסק נוצר רק דרך `create_business`, וצירוף משתמש רק דרך `add_member_by_email`; אין הרשאת INSERT ישירה.
- האפליקציה משתמשת רק במפתח הציבורי ובסשן של המשתמש. אין שימוש ב-service role.
- קוד השרת קורא את המשתמש והעסק הפעיל דרך `src/lib/auth.ts`; מזהה העסק לעולם לא מגיע מהטופס.
