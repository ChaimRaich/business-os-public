# Business OS — Inventory

ניהול עסק קטן ובינוני במקום אחד: מלאי, קמפיינים וראיית חשבון. האפיון המלא ב-[SPEC.md](SPEC.md).

## Stack

- Next.js 16 (App Router, Cache Components), React 19, Tailwind 4, עברית RTL
- Supabase: Postgres, Auth, Row Level Security, מיגרציות SQL ב-`supabase/migrations`

## הרצה מקומית

דרוש Docker פועל (למשל `colima start`).

```bash
npm install
npx supabase start          # מסד, Auth ו-Studio מקומיים; מריץ את המיגרציות
cp .env.example .env.local  # ולהדביק את ה-Publishable key מתוך `npx supabase status`
npm run dev                 # http://localhost:3000
```

Studio: http://127.0.0.1:54323 · אימיילים מקומיים (Mailpit): http://127.0.0.1:54324

## תחומים

התפריט העליון מחולק לתחומי העסק (`src/components/main-nav.tsx`): **מלאי** (מוצרים, קליטה, ספקים, ייצוא לקופה, מכירות), **קמפיינים** ו**ראיית חשבון**. המסך הראשי מציג לכל תחום מה מחכה לטיפול.

### ראיית חשבון

- פתוח לבעלים ולמנהל בלבד, גם במסך וגם ב-RLS (`expenses`, `document_payments`).
- מסמכי ספקים מגיעים מהקליטות המאושרות דרך ה-view ‏`accounting_purchases` (‏`security_invoker`, כך שההרשאות של `documents` חלות). הסכום לפני מע״מ הוא הסיכום המודפס במסמך, ואם אין, סכום השורות. מע״מ נספר רק בחשבונית מס או חשבונית מס / קבלה.
- מועד תשלום ו״שולם״ נשמרים ב-`document_payments`, ליד המסמך, כי מסמך מאושר נעול.
- תקופות: חודש (`?period=2026-11`) או דו־חודשי (`?period=2026-11-2`). `/accounting/export` מוריד את התקופה כ-`.xlsx`.
- זה ריכוז חומר לרואה החשבון, לא הנהלת חשבונות: אין הפקת מסמכי מס ואין הכנסות.

### קמפיינים

- `campaigns` ו-`campaign_posts`. כל חבר בעסק מתכנן וכותב; רק בעלים ומנהל מוחקים קמפיין. מצב הקמפיין (מתוכנן / פעיל / הסתיים) נגזר מהתאריכים.
- אין חיבור לרשתות: פוסט מסומן ״פורסם״ ידנית (`published_at`, `published_url`).
- הצעת טקסט (`src/lib/ai-text.ts`) משתמשת באותו מודל שקורא מסמכים, ומקבלת רק עובדות מהמערכת ומה שהמשתמש כתב.

## קטלוג

- **מוצר** הוא דגם; כל פריט שנמכר הוא **וריאציה** שלו (מידה, צבע). למוצר תמיד יש לפחות וריאציה אחת.
- לכל וריאציה כמה **קודים** שרוצים: ברקוד, מק״ט ספק, מק״ט קופה, מזהה באתר. הקוד נשמר כטקסט בדיוק כפי שהודפס (אפסים מובילים נשמרים); ההתאמה והחיפוש מתעלמים מאותיות גדולות/קטנות.
- ברקוד, מק״ט קופה ומזהה באתר ייחודיים בעסק. מק״ט ספק הוא קוד דגם ויכול לחזור בכמה וריאציות.
- חיפוש (`search_products`) לפי שם מוצר, שם ספק, שם וריאציה או חלק מכל קוד.
- לכל עסק נוצר מחסן ברירת מחדל; מחסנים נוספים מנוהלים בהגדרות.

## קליטת סחורה

- מעלים צילום או PDF של תעודת משלוח / חשבונית (עד 10 קבצים למסמך). הקבצים נשמרים באחסון פרטי תחת `<business_id>/<document_id>/`.
- Claude קורא את המסמך ומחזיר שורות מובנות: מק״ט ספק, ברקוד, תיאור, וריאציה, כמות, עלות לפני מע״מ ומחיר צרכן. ערך שלא מודפס נשאר ריק; ערך שלא נקרא בוודאות מסומן לבדיקה.
- במסך האימות עורכים את השורות מול המסמך המקורי. המערכת מתריעה על אי-התאמה בין השורות לסכומים המודפסים ועל מסמך שכבר הועלה.
- כל שורה מותאמת לקטלוג לפי ברקוד, ואם אין, לפי מק״ט ספק: כשהוא מצביע על וריאציה אחת, או כשהווריאציה שבשורה זהה לשם הווריאציה בקטלוג.
- שורות שאינן בקטלוג מוסיפים בלחיצה אחת (`create_products_from_lines`): שורות עם אותו מק״ט ספק הופכות לווריאציות של מוצר אחד. שורה בלי מק״ט ובלי ברקוד לא נוספת אוטומטית.

## מלאי

- **אישור קליטה** (`approve_document`) כותב תנועת מלאי לכל שורה ומעלה את היתרה במחסן, באותה טרנזקציה. נדרש שכל השורות יהיו בקטלוג ועם כמות חיובית.
- האישור חד-פעמי: קריאה חוזרת לא משנה כלום, ומסמך של אותו ספק עם אותו מספר לא נקלט פעמיים.
- מסמך מאושר ננעל: אי אפשר לערוך, למחוק או להחזיר אותו לבדיקה. מוצר שיש לו תנועות לא נמחק.
- **תיקון מלאי** (`adjust_stock`) בדף המוצר, לבעלים ולמנהל בלבד, עם סיבה חובה. התיקון נרשם כתנועה.
- `stock_movements` הוא יומן להוספה בלבד ו-`stock_levels` היא היתרה. אף משתמש לא כותב אליהם ישירות, רק שתי הפונקציות האלה.
- עדיין אין הפחתת מלאי ממכירות, ולכן היתרה היא ״מה שנקלט״ ולא מלאי בזמן אמת.

## קובץ לקופה

- ממסמך מאושר מכינים קובץ `.xls` (Excel 97-2003) ב-12 העמודות שהקופה מקבלת (SPEC 13.4): שורה לכל פריט, כמויות של אותו פריט מסוכמות.
- **כללים לכל ספק** (בכרטיס הספק): קוד ושם הספק בקופה; ברקוד פנימי (אות ומספר רץ, מתקדם לבד) או הברקוד / קוד הפריט של הספק; תמחור לפי מכפלה על העלות או לפי מחיר הצרכן המודפס. מחיר מכירה = מחיר מועדון + 10%, בשקלים שלמים.
- **מחלקות הקופה** מוגדרות בהגדרות (בעלים ומנהל). המחלקה, שם הפריט והמחירים נשמרים על המוצר ומוצעים שוב בפעם הבאה.
- פריט מקבל ברקוד קופה פעם אחת ושומר עליו בכל קובץ נוסף.
- כל קובץ נשמר ב-`pos_exports` בדיוק כפי שנוצר. הורדה חוזרת מחזירה אותו קובץ ולא משנה מלאי. הקובץ נשאר ״ממתין להעלאה״ עד שהמשתמש מסמן שהקופה קלטה אותו.
- הקובץ נכתב בספריית `xlsx` (SheetJS 0.18.5 מ-npm). ל-`npm audit` יש עליה התרעה שנוגעת לקריאת קבצים לא מהימנים; כאן היא רק כותבת.

### ייצוא והיסטוריה

- המסך `/exports` מציג את כל הקבצים שהוכנו לקופה, עם סינון לפי סטטוס: ממתין, תקלה, נקלט. בראשו רשימת הקליטות שאושרו ועוד לא הוכן להן קובץ.
- קובץ נשאר "ממתין להעלאה לקופה" עד שהמשתמש מסמן אחת משתיים: "הקובץ נקלט בקופה" (`confirm_pos_export`), או "הקופה לא קיבלה את הקובץ" עם תיאור התקלה (`report_pos_export_problem`). אף אחת מהן לא נוגעת במלאי.
- קליטה נחשבת "נקלטה בקופה" כשאחד הקבצים שלה אושר; אחרת קובע הקובץ האחרון. הסטטוס מוצג גם ברשימת הקליטות, במסמך ובהיסטוריית הקליטות שבכרטיס הספק.

## מכירות וחיבורים

- **ייבוא דוח מכירות (`/sales/import`):** מעלים דוח מכירות מהקופה ברמת פריט (xls, xlsx או CSV, כולל CSV בקידוד windows-1255). הקובץ נקרא בדפדפן; לשרת נשלחות רק שורות. המשתמש בוחר איזו עמודה היא הקוד, הכמות, מספר העסקה, התאריך והמחיר, והבחירה נשמרת בדפדפן לדוח הבא. אין הנחה על מבנה דוח מסוים.
- **הורדה מהמלאי (`import_sales`):** כל שורה שזוהתה יוצרת תנועת `sale` (או `return` לכמות שלילית) ומעדכנת את היתרה באותה פעולה. הזיהוי לפי מק״ט קופה, ואם אין, לפי ברקוד.
- **בלי הפחתה כפולה:** טביעת האצבע היא של השורות (מחסן, תאריך, קוד, כמות), לא של הקובץ, כי הקופה חותמת את שעת הייצוא בקובץ. כשבדוח אין תאריך (הדוח האמיתי של הקופה, SPEC 13.5) המשתמש בוחר את היום שהדוח מסכם, ומתקבל דוח אחד ליום ולמחסן. כשיש מספר עסקה, אותה מכירה בדוח חופף מדולגת.
- **ביטול ייבוא (`revert_sales_import`, בעלים ומנהל):** מחזיר את המלאי בתנועות `adjustment` עם סיבה, משחרר את היום לייבוא מחדש, ומשאיר את הדוח ברשימה כ״בוטל״.
- **לא פריט מלאי (`ignore_sales_code`):** קוד שאינו סחורה (״פריט כללי״, שירותים) נשמר ב-`sales_ignored_codes` ומדולג בכל ייבוא.
- **מכירות שלא זוהו:** קוד שאינו בקטלוג נשמר בלי תנועת מלאי ומוצג ב-`/sales`. אחרי שמוסיפים את הקוד לפריט, ״ניסיון זיהוי מחדש״ (`rematch_sales_lines`) מוריד אותן מהמלאי, פעם אחת.
- **מצב החיבורים (`/settings/connections`):** לקופה, בשני הכיוונים: עדכון אחרון, פעולות ממתינות ותקלות. כשלא יובא דוח מכירות שבוע, המלאי מסומן כלא מעודכן.
- **אתר המסחר (WooCommerce), מהאתר למערכת בלבד:** בעלים או מנהל מזין במסך החיבורים את כתובת האתר ומפתח REST בהרשאת **קריאה**. ״סנכרון עכשיו״ קורא את ההזמנות שהשתנו מאז הסנכרון הקודם ומוריד אותן מהמלאי. הקוד ב-`src/lib/woocommerce.ts` שולח בקשות GET בלבד; המערכת לא כותבת לאתר ולא מעדכנת בו מלאי.
  - **בלי כפילויות (`record_web_sync`):** לכל שורת הזמנה נשלחת הכמות שצריכה להיות מחוץ למדף כרגע (0 להזמנה שבוטלה או הוחזרה במלואה, ובניכוי החזר חלקי), ונרשם רק ההפרש ממה שכבר נרשם. סנכרון חוזר, תשלום מאוחר, ביטול ושחזור הזמנה לא סופרים דבר פעמיים.
  - **מה נחשב מכירה:** הזמנה בסטטוס processing, completed או on-hold. הזמנות שנוצרו לפני ״תאריך ההתחלה״ של החיבור לא נוגעות במלאי.
  - **זיהוי פריט:** לפי ה-SKU באתר, מול ״מזהה באתר״, ואז מק״ט קופה, ואז ברקוד. למוצר בלי SKU הקוד הוא `#` ומספר המוצר באתר.
  - **המפתח** נשמר מוצפן ב-Supabase Vault. רק בעלים ומנהל יכולים לשמור אותו או להשתמש בו; שאר חברי העסק רואים את מצב החיבור ואת ארבעת התווים האחרונים של המפתח.
  - **כתובת האתר** חייבת להיות אתר https ציבורי (לא כתובת IP ולא שרת פנימי), והמפתח לא נשלח הלאה בהפניה לכתובת אחרת.
  - **בדיקה:** `npm run test:woo` מריץ את הקורא מול שרת דמה מקומי ואת הרישום מול ה-Supabase המקומי.

## חוסרים ודוחות

- **סף חוסר:** לכל פריט אפשר לקבוע סף בדף המוצר (`product_variants.low_stock_threshold`); פריט בלי סף משלו משתמש בסף הכללי של העסק (`businesses.low_stock_default`, בעלים בלבד, במסך ההגדרות).
- **מסך החוסרים (`/reports/stock`, `stock_overview`):** פריטים במינוס, שאזלו, או שהגיעו לסף. נבדקים רק פריטים שיש להם תנועות מלאי; פריט בקטלוג שמעולם לא נקלט אינו ״אזל״. המסך מציין עד מתי המלאי מעודכן, לפי דוח המכירות האחרון.
- **דוח מכירות (`/reports/sales`, `sales_report`):** יחידות שנמכרו והוחזרו בתקופה, לפי מוצר או לפי ספק, מהקופה ומהאתר. נספרות רק מכירות שזוהו בקטלוג ושהייבוא שלהן לא בוטל. הסכום הוא כמות כפול המחיר שבדוח המקור (בדוח הקופה: מחיר מחירון), לא הפדיון בפועל.
- **במסך הראשי:** מספר הפריטים במינוס, שאזלו ושמתחת לסף מופיע ב״מה מחכה לטיפול״.
- ההתראות הן בתוך המערכת בלבד. שליחה במייל או בהודעה, וטיוטת הזמנה לספק, לא נבנו.

### חיבור למודל

מגדירים ב-`.env.local` אחת משלוש האפשרויות (פירוט ב-`.env.example`):

- **Claude ב-Azure (Microsoft Foundry):** `ANTHROPIC_FOUNDRY_API_KEY`, `ANTHROPIC_FOUNDRY_RESOURCE`, ו-`EXTRACTION_MODEL` = שם ה-deployment.
- **Claude ב-Anthropic API:** `ANTHROPIC_API_KEY`.
- **מודל אחר ב-Azure שקורא תמונות (למשל Kimi-K3.1-Pro):** `AZURE_AI_ENDPOINT` (ה-Target URI מעמוד ה-deployment), `AZURE_AI_API_KEY`, ו-`EXTRACTION_MODEL` = שם ה-deployment. במסלול הזה כל עמוד PDF מומר לתמונה לפני השליחה.

כשמוגדרת יותר מאפשרות אחת, Claude קודם. לפני שמחליפים מודל מריצים את בדיקת האיכות שלמטה.

בלי מפתח, מסמך שמועלה מסומן "הקריאה נכשלה" עם הסבר, ואפשר להזין את השורות ידנית.

### בדיקת איכות החילוץ

```bash
npm run eval:extraction -- path/to/invoice.pdf
```

מריץ חילוץ אמיתי ומשווה שורה-שורה לתוצאה הצפויה שב-`SPEC.md` (סעיפים 13.1, 13.2). כל הרצה צורכת קרדיט.

## הפרדת נתונים והרשאות

- כל טבלה עסקית נושאת `business_id`; מדיניות RLS מתירה גישה רק לחברי העסק דרך `private.is_member` / `private.role_in`.
- תפקידים: `owner` (בעלים), `manager` (מנהל), `staff` (עובד). רק בעלים משנה שם עסק ומנהל משתמשים; בעלים ומנהל מוחקים מוצרים ומנהלים מחסנים; כל חבר בעסק מוסיף ועורך מוצרים וספקים.
- שורות בנות (וריאציות, קודים) מצביעות על האב דרך `(id, business_id)`, כך ששורה לא יכולה להתחבר לנתונים של עסק אחר.
- עסק נוצר רק דרך `create_business`, וצירוף משתמש רק דרך `add_member_by_email`; אין הרשאת INSERT ישירה.
- האפליקציה משתמשת רק במפתח הציבורי ובסשן של המשתמש. אין שימוש ב-service role.
- קוד השרת קורא את המשתמש והעסק הפעיל דרך `src/lib/auth.ts`; מזהה העסק לעולם לא מגיע מהטופס.
